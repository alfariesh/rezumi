Reactive Resume deploys to Cloudflare Workers only. Three things guard that deployment: the `check:cloudflare` build check, the `test:cloudflare` smoke test, and the deploy workflow that publishes `main`. The first two run in the **CI** workflow (`.github/workflows/ci.yml`) on every pull request, and you can run them on your own machine. For setup of the Worker itself, see [Self-hosting on Cloudflare](/self-hosting/cloudflare).

## Build check

`pnpm check:cloudflare` builds the web app and the Worker into `apps/server/dist-cloudflare`, then runs `wrangler deploy --dry-run`. Wrangler validates `wrangler.jsonc`, bundles the Worker, WebAssembly PDF engine, prompt files and static assets, and reports problems without publishing anything.

```bash
pnpm check:cloudflare
```

It needs no Cloudflare account, no deployment credentials and no database, so pull requests from forks run it safely. It does not mutate any database.

## Smoke test

`pnpm test:cloudflare` runs `tooling/cloudflare/smoke.mjs` against the **built** Worker and its emulated local bindings (R2, Durable Objects and Hyperdrive), using Wrangler's test harness rather than a Node mock of Workers.

```bash
pnpm build:cloudflare
pnpm test:cloudflare
```

The script creates a new disposable PostgreSQL database, applies the repository's migrations to it, runs the checks, and deletes the database afterwards. It covers:

- authentication and sessions;
- native cron reminders and duplicate protection;
- resume transactions;
- R2 uploads and access control;
- live resume updates;
- PDF pictures;
- assistant streaming and cancellation;
- atomic counters across Durable Object eviction, and state expiry.

<Warning>
  The smoke test needs a **local** disposable PostgreSQL admin connection and refuses any other host. By default it uses
  the development Compose PostgreSQL on `localhost:5432` (see [Development setup](/contributing/development)). Set
  `CLOUDFLARE_TEST_DATABASE_ADMIN_URL` to use another local server. It never deploys to Cloudflare.
</Warning>

### In CI

The `check-cloudflare` job in the **CI** workflow starts an isolated PostgreSQL service, installs dependencies, then runs `pnpm check:cloudflare` followed by `pnpm test:cloudflare`. It runs on every pull request and every push to `main`, alongside the unit and browser test jobs.

### When the build check fails

The Worker is bundled by `tooling/cloudflare/build.mjs` (esbuild) from `apps/server/src/cloudflare/index.ts`. A new server dependency can break the check if it needs Node.js APIs that Workers does not provide, or loads native or non-bundlable files at runtime. Read the error from `pnpm build:cloudflare` or the Wrangler dry run first; then resolve it with a Workers-compatible alternative, an alias in the build script (as is done for `sharp`), or an additional module rule in `wrangler.jsonc`.

## Deploy workflow

`.github/workflows/deploy-cloudflare.yml` ("Deploy to Cloudflare") runs on every push to `main` and on manual dispatch. Runs never overlap: a deployment already in progress finishes before the next one starts. The single job:

1. Checks out the source, installs pnpm and Node.js (from `.nvmrc`), and runs `pnpm install --frozen-lockfile`.
2. Applies database migrations with `pnpm --filter @reactive-resume/db db:migrate`, only when the `DATABASE_URL` secret is set.
3. Runs `pnpm deploy:cloudflare`, which builds the Worker and publishes it with Wrangler.

It reads three repository secrets:

| Secret                  | Purpose                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------ |
| `CLOUDFLARE_API_TOKEN`  | Lets Wrangler publish the Worker.                                                                |
| `CLOUDFLARE_ACCOUNT_ID` | The Cloudflare account that owns the Worker, Hyperdrive configuration and R2 bucket.             |
| `DATABASE_URL`          | A direct (non-pooled) PostgreSQL connection string, used only to apply migrations before deploy. |

The Worker's runtime secrets (`AUTH_SECRET`, `ENCRYPTION_SECRET`, SMTP and OAuth credentials) are not repository secrets. Store them on the Worker with `wrangler secret put`; plain variables live in `wrangler.jsonc`.

After a deployment, open `/api/health` and check that database and storage report `healthy` with storage type `r2`, then follow the checks in [Self-hosting on Cloudflare](/self-hosting/cloudflare#check-the-installation).
