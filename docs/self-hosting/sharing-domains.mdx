---
title: "Sharing domains"
description: "Serve public resume pages on an alias domain, enable users' own domains with DNS verification and HTTPS, and troubleshoot sharing after an upgrade."
---

Use this guide when you operate a Rezumi Worker on Cloudflare and want a shorter public address or want users to connect
their own domains. Ordinary public resume links work with `APP_URL` alone. Domain settings are optional.

## Choose which address you need

| Address                                                      | Purpose                                       | What it serves                                                                  |
| ------------------------------------------------------------ | --------------------------------------------- | ------------------------------------------------------------------------------- |
| `APP_URL`, such as `https://resume.example.com`              | Your main application address                 | Sign-in, editor, public pages and API                                           |
| `APP_ALIAS_URL`, such as `https://cv.example.com`            | One shorter address for everyone              | The same public pages; sign-in and editor redirect to `APP_URL`                 |
| A user's verified domain, such as `https://jane.example.net` | One account's personal resume site            | That account's primary resume at `/`                                            |
| `ROOT_RESUME_ID`                                             | Turn your instance's homepage into one resume | The selected public resume at `/`, while the application keeps its usual routes |

An alias doesn't move accounts or create another database. A custom domain doesn't host the editor. Choose
`ROOT_RESUME_ID` for a personal instance that only needs its own homepage; see
the `ROOT_RESUME_ID` variable in the [environment reference](/self-hosting/environment-variables#server).

## Add an alias domain

1. Add the alias hostname to the same Worker: in the Cloudflare dashboard open the Worker, then **Settings → Domains &
   Routes**, and add it as a **Custom Domain**. The domain's DNS zone must be on Cloudflare. Cloudflare issues and
   renews the HTTPS certificate for it. The Worker receives the incoming hostname unchanged, so the app can tell the two
   addresses apart.
2. Set the alias in `vars` in `wrangler.jsonc`, next to `APP_URL`, and redeploy with `pnpm deploy:cloudflare`:

   ```jsonc
   "vars": {
     "APP_URL": "https://resume.example.com",
     "APP_ALIAS_URL": "https://cv.example.com"
   }
   ```

3. Open a published resume at `https://cv.example.com/<username>/<slug>`. It should show the same page as the main
   address. Open `/auth/login` on the alias; it should redirect to your main domain.

The **Share** mode copies the alias when configured. Public pages, the homepage and marketing pages remain available
on both domains. Canonical metadata points search engines to `APP_URL`, except when a primary resume has its own
verified custom domain. Keep `APP_URL` as the sign-in origin; cookies, passkeys and OAuth callbacks belong there.

## Enable users' custom domains

### Before you start

- Have a hostname such as `domains.example.com` on a Cloudflare-managed zone, attached to the Worker as a **Custom
  Domain**. This is the CNAME target users will see; it isn't itself a user's custom domain.
- Have a way to deliver each verified user hostname to the Worker with a valid certificate. On Cloudflare this is
  [Cloudflare for SaaS custom hostnames](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/),
  with the target hostname above as the fallback origin. The app verifies ownership and serves the right resume by
  hostname, but it does not call the Cloudflare API: you add each hostname to Cloudflare yourself, or with your own
  automation. Environment variables alone don't configure DNS or TLS.

<Note>
  The app's built-in router endpoint (`/api/internal/traefik`) returns Traefik-format configuration and is not used on
  Cloudflare. Without a provider polling it, the background DNS rechecks described under [Keep domains
  working](#keep-domains-working) do not run, so check a domain with **Check DNS** after DNS changes.
</Note>

### Set the app's environment

Add the target to `vars` in `wrangler.jsonc`, then store a secret for the controls to unlock:

```jsonc
"vars": { "CUSTOM_DOMAIN_TARGET": "domains.example.com" }
```

```bash
openssl rand -hex 32 | pnpm exec wrangler secret put CUSTOM_DOMAIN_PROVIDER_SECRET
```

Use a hostname for `CUSTOM_DOMAIN_TARGET`, without a scheme, path or port. Redeploy after changing `vars`. Both settings
must be present before the custom-domain controls become available on web and mobile. The secret is only checked on the
Traefik-format endpoint, which Cloudflare doesn't use; keep it out of URLs, public configuration and logs anyway.

### Verify one domain end to end

1. Publish a test resume and turn on **Primary resume** in **Share**.
2. Under **Your domain**, enter a domain you control and select **Connect**.
3. At the domain's DNS provider, add the exact ownership TXT record shown in Share, plus its routing record:

   | Record | Name                                                    | Value                                                   |
   | ------ | ------------------------------------------------------- | ------------------------------------------------------- |
   | CNAME  | The chosen subdomain, such as `resume.jane.example.net` | Your `CUSTOM_DOMAIN_TARGET`                             |
   | TXT    | `_rx-verify.resume.jane.example.net`                    | The account-specific `rx-verify=…` value shown in Share |

   For a root domain, use A and/or AAAA records instead of CNAME. Every address returned for the custom domain must
   be among the target hostname's current addresses. Keep the TXT record too. If a DNS service proxies the record
   and hides the target addresses, use DNS-only records for this check.

4. Select **Check DNS**. Wait for DNS propagation and try again if the records aren't visible yet.
5. After verification, add the hostname to Cloudflare for SaaS (see above), then allow the app's hostname cache (up to a
   minute) and certificate issuance to complete. Open `https://<custom-domain>/` from a signed-out browser.
6. Check that the primary resume appears, its password and contact settings apply, and its PDF downloads follow
   **Visitors can download the PDF**. Check HTTPS separately: successful DNS verification doesn't prove a certificate
   was issued.

Each account stores one domain. Verification proves ownership using the TXT record and routing using CNAME or
addresses. A verified domain can move to another account only after that account supplies its own valid DNS proof.
Paths other than `/`, public PDF routes and favicons redirect to the main application, except `/robots.txt`.

### Keep domains working

Leave the ownership TXT and routing records in place. With a router provider polling the app, background rechecks run for verified
domains not checked within a day. After a domain's DNS fails verification continuously for seven days, its verification
and router are removed. Restoring DNS and choosing **Check DNS** reconnects it. Without provider polling, those
background rechecks don't run.

Turning off a resume's public link keeps the domain connected but shows an unavailable page. Changing the primary
resume moves the domain's homepage to that resume. Removing the domain in Share removes the connection; normal
public resume addresses keep working. A hostname may remain in the app's cache for up to a minute.

## Upgrade an existing installation

v6.0.7 adds a `custom_domain` table and the `show_in_search_engines`, `hide_contact_details` and `is_primary` resume
columns. Back up your database, then run `pnpm --filter @rezumi/db db:migrate` before deploying the new Worker. Deploy the backend before
mobile updates that use the new sharing controls.

Existing resumes retain public/private status and download settings. Search indexing and contact hiding default
to off, and no resume becomes primary automatically. Existing public addresses stay valid, including older
addresses longer than 64 characters. New or changed addresses use lowercase letters and numbers separated by
single dashes, up to 64 characters. A renamed address redirects for 30 days.

No new domain variables are required if you keep using your main address. Existing public links now show responsive
HTML resume pages; the public PDF remains a separate download. Check that your Worker routes send both resume paths and
their `/api/resumes/…` requests to the app. If you maintain an API client, see
[sharing API behavior](/guides/using-the-api#public-sharing-settings).

## Troubleshoot

| Symptom                                   | Check                                                                                                                                                    |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Your domain** is missing                | Set both custom-domain settings and redeploy the Worker.                                                                                                 |
| **Check DNS** says records aren't visible | Verify the exact TXT name/value, the CNAME target or all A/AAAA addresses, and DNS propagation. Keep DNS-only routing where a proxy hides those records. |
| Domain is connected but HTTPS fails       | Check that the hostname is added in Cloudflare for SaaS, its certificate status, and that the fallback origin is your target hostname.                   |
| Domain opens an unavailable page          | Publish a resume and make it primary; also check whether it is in Trash.                                                                                 |
| Alias opens the wrong site                | Attach the alias as a Custom Domain on the same Worker and check its certificate.                                                                        |
| Owner visit is counted                    | Sign-in cookies belong to the main origin; an alias or custom domain can see an anonymous visitor.                                                       |
