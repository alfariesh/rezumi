Use this guide when you operate a Rezumi Worker on Cloudflare and want a shorter public address or want users to connect
their own domains. Ordinary public resume links work with `APP_URL` alone. Domain settings are optional.

## Choose which address you need

| Address                                                      | Purpose                                       | What it serves                                                                  |
| ------------------------------------------------------------ | --------------------------------------------- | ------------------------------------------------------------------------------- |
| `APP_URL`, such as `https://resume.example.com`              | Your main application address                 | Sign-in, editor, public pages and API                                           |
| `APP_ALIAS_URL`, such as `https://cv.example.com`            | One shorter address for everyone              | The same public pages; sign-in and editor redirect to `APP_URL`                 |
| A user's verified domain, such as `https://www.jane.example` | One account's personal site                   | That account's published portfolio at `/`, or else its primary resume           |
| `ROOT_RESUME_ID`                                             | Turn your instance's homepage into one resume | The selected public resume at `/`, while the application keeps its usual routes |

An alias doesn't move accounts or create another database. A custom domain doesn't host the editor. Choose
`ROOT_RESUME_ID` for a personal instance that only needs its own homepage; see
the `ROOT_RESUME_ID` variable in the [environment reference](/self-hosting/environment-variables#server).

## Add an alias domain

1. Add the alias hostname to the same Worker: in the Cloudflare dashboard open the Worker, then **Settings → Domains &
   Routes**, and add it as a **Custom Domain**. The domain's DNS zone must be on Cloudflare. Cloudflare issues and
   renews the HTTPS certificate for it. The Worker receives the incoming hostname unchanged, so the app can tell the two
   addresses apart.
2. Set the alias in `vars` in `wrangler.jsonc`, next to `APP_URL`, and redeploy with `pnpm deploy:cloudflare`:

   ```jsonc
   "vars": {
     "APP_URL": "https://resume.example.com",
     "APP_ALIAS_URL": "https://cv.example.com"
   }
   ```

3. Open a published resume at `https://cv.example.com/<username>/<slug>`. It should show the same page as the main
   address. Open `/auth/login` on the alias; it should redirect to your main domain.

The **Share** mode copies the alias when configured. Public pages, the homepage and marketing pages remain available
on both domains. Canonical metadata points search engines to `APP_URL`, except when a primary resume has its own
verified custom domain. Keep `APP_URL` as the sign-in origin; cookies, passkeys and OAuth callbacks belong there.

## Enable users' custom domains

### Before you start

Users' domains reach your Worker through [Cloudflare for SaaS](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/). You need a zone on Cloudflare, here `example.com`, with the Worker's main domain attached as a **Custom Domain**. Cloudflare includes 100 custom hostnames and bills the ones after that per month; check the current [plans](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/plans/).

When both the zone ID and the API token below are set, the app creates each hostname through the API once DNS proves who owns the domain, follows its certificate until it's active, and deletes it when the domain goes. Without them it verifies DNS only, and you add each hostname to Cloudflare yourself.

### Set up Cloudflare for SaaS

1. Open the zone, then **SSL/TLS → Custom Hostnames**, and enable Cloudflare for SaaS.
2. Create a target hostname that has no origin server: in **DNS → Records** add a proxied `AAAA` record for `domains` with the value `100::`. Back in **Custom Hostnames**, enter `domains.example.com` as the **Fallback Origin** and wait until it's **Active**. Users point their CNAME records here.
3. In **Workers Routes** on the zone, add these routes **in this order**. The ones without a Worker come first so your own subdomains never pass through this Worker, not even for a moment:

   | Route                            | Worker   | Why                                                              |
   | -------------------------------- | -------- | ---------------------------------------------------------------- |
   | `*/.well-known/acme-challenge/*` | None     | Certificate validation has to reach Cloudflare, not the app      |
   | `*/.well-known/pki-validation/*` | None     | Certificate validation has to reach Cloudflare, not the app      |
   | `example.com/*`                  | None     | The Worker's own Custom Domain already serves this               |
   | `*.example.com/*`                | None     | Leaves your blog and other subdomains as they are                |
   | `domains.example.com/*`          | Your app | Users whose DNS is also on Cloudflare arrive under this hostname |
   | `*/*`                            | Your app | Every other hostname: your users' domains                        |

   Keep these routes in the dashboard rather than in `wrangler.jsonc`, so the deploy token needs no zone permissions. After adding them, open your main domain and your subdomains to check they still work.

4. Create an API token under **My Profile → API Tokens** with one permission, **Zone → SSL and Certificates → Edit**, limited to this zone. Store it yourself:

   ```bash
   pnpm exec wrangler secret put CLOUDFLARE_SAAS_API_TOKEN
   ```

### Set the app's environment

Add the target and the zone ID from the zone's **Overview** page to `vars` in `wrangler.jsonc`, then redeploy:

```jsonc
"vars": {
  "CUSTOM_DOMAIN_TARGET": "domains.example.com",
  "CLOUDFLARE_SAAS_ZONE_ID": "<32-character zone ID>"
}
```

Use a hostname for `CUSTOM_DOMAIN_TARGET`, without a scheme, path or port. Apply database migrations before deploying. Until the token exists, the zone ID does nothing.

With the automation on, custom domains are offered only to accounts that `PORTFOLIO_MODE` lets in, because each hostname can cost money: `off` hides them, `admins` shows them to admins, and `on` shows them to everyone, with the plan rule below.

<Note>
  Addresses that aren't connected answer `404` once the automation is on, instead of showing the app. Direct visits to
  the target hostname redirect to `APP_URL`.
</Note>

### Verify one domain end to end

1. Publish a test portfolio, or a test resume with **Primary resume** turned on in **Share**.
2. Under **Your domain**, enter a domain you control and select **Connect**.
3. At the domain's DNS provider, add both records shown:

   | Record | Name                                        | Value                                          |
   | ------ | ------------------------------------------- | ---------------------------------------------- |
   | CNAME  | The chosen name, such as `www.jane.example` | Your `CUSTOM_DOMAIN_TARGET`                    |
   | TXT    | `_rx-verify.www.jane.example`               | The account-specific `rx-verify=…` value shown |

   If that DNS is also on Cloudflare, set the CNAME to **DNS only**.

4. Select **Check DNS**. The status then moves through **DNS points here**, **Ownership proven** and **HTTPS certificate** to **Active**, usually within minutes. The page updates by itself.
5. Open `https://<custom-domain>/` from a signed-out browser. Check that the padlock appears and the right page opens. Remove the domain and check that the hostname disappears from **Custom Hostnames** within a couple of minutes.

A domain without `www` needs a CNAME at the root, which only some DNS providers allow (Cloudflare calls this flattening). Proxying a root domain with static addresses is an Enterprise feature, so suggest `www` or another subdomain and forwarding the root at the registrar. Without the automation, a root domain uses `A` and/or `AAAA` records instead, and every address returned must be among the target hostname's current addresses.

Each account stores one domain. Verification proves ownership using the TXT record and routing using CNAME or addresses. A verified domain can move to another account only after that account supplies its own valid DNS proof, and its hostname moves with it. Paths other than `/`, public PDF routes, portfolio requests and favicons redirect to the main application, except `/robots.txt`.

### Keep domains working

Leave the ownership TXT and routing records in place. A job checks every verified domain daily, and follows new hostnames every couple of minutes. After a domain's DNS fails continuously for seven days, its verification is removed and its hostname deleted; restoring DNS and choosing **Check DNS** connects it again.

With the automation, where portfolios are on and a plan includes custom domains, a domain keeps working for seven days after the plan ends, then redirects to the account's address on `APP_URL`. Thirty days after that its hostname is deleted, while the domain stays on the account. Renewing brings it back without any DNS change.

Without the automation, the job doesn't touch DNS or hostnames, and rechecks only run while something polls the app's Traefik-format endpoint (`/api/internal/traefik`, which Cloudflare doesn't use). Check a domain with **Check DNS** after DNS changes.

Turning off a resume's public link or unpublishing a portfolio keeps the domain connected. Removing the domain removes the connection and its hostname; normal public addresses keep working. A hostname may remain in the app's cache for up to a minute.

## Upgrade an existing installation

v6.0.7 adds a `custom_domain` table and the `show_in_search_engines`, `hide_contact_details` and `is_primary` resume
columns. Back up your database, then run `pnpm --filter @rezumi/db db:migrate` before deploying the new Worker. Deploy the backend before
mobile updates that use the new sharing controls.

Existing resumes retain public/private status and download settings. Search indexing and contact hiding default
to off, and no resume becomes primary automatically. Existing public addresses stay valid, including older
addresses longer than 64 characters. New or changed addresses use lowercase letters and numbers separated by
single dashes, up to 64 characters. A renamed address redirects for 30 days.

No new domain variables are required if you keep using your main address. Existing public links now show responsive
HTML resume pages; the public PDF remains a separate download. Check that your Worker routes send both resume paths and
their `/api/resumes/…` requests to the app. If you maintain an API client, see
[sharing API behavior](/guides/using-the-api#public-sharing-settings).

## Troubleshoot

| Symptom                                   | Check                                                                                                                                                                      |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Your domain** is missing                | Set `CUSTOM_DOMAIN_TARGET` and either the Cloudflare for SaaS settings or `CUSTOM_DOMAIN_PROVIDER_SECRET`, and redeploy. With the automation, also check `PORTFOLIO_MODE`. |
| **Check DNS** says records aren't visible | Verify the exact TXT name and value, the CNAME target, and DNS propagation. Set the CNAME to DNS only where a proxy hides it.                                              |
| Status stays on **HTTPS certificate**     | Look at the hostname in **Custom Hostnames**. Check that the two `/.well-known/` routes have no Worker, and look for CAA records on the domain.                            |
| HTTPS fails for every domain              | Check that the fallback origin is **Active** and that the `*/*` route points at your Worker.                                                                               |
| Hostnames aren't created                  | Search the Worker's logs for `[custom-domain]`. An `auth` failure means the token is wrong; `quota` means the zone's custom hostname limit.                                |
| Your own subdomain shows the app or a 404 | Add a route for it with no Worker, as in the setup table.                                                                                                                  |
| Domain opens an unavailable page          | Publish a portfolio, or publish a resume and make it primary; also check whether it is in Trash.                                                                           |
| Alias opens the wrong site                | Attach the alias as a Custom Domain on the same Worker and check its certificate.                                                                                          |
| Owner visit is counted                    | Sign-in cookies belong to the main origin; an alias or custom domain can see an anonymous visitor.                                                                         |
